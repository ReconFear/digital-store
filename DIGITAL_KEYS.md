# Digital Store — автоматическая выдача цифровых ключей (PR5)

Модуль выдаёт покупателю ключи товара (лицензии, коды активации) после подтверждённой оплаты. Ключи хранятся зашифрованными. Выдача атомарна: ключ не уходит двум покупателям, а оплаченная позиция не остаётся «выполненной» без ключей.

Контракт API для frontend — отдельный документ `FRONTEND_DELIVERY_API.md`.

## 1. Как это устроено

```text
Администратор (CLI, свой компьютер)        База (PostgreSQL)                     Процессы магазина
───────────────────────────────────        ──────────────────                    ─────────────────
файл ключей ──► нормализация                digital_key_batches (партии)
            ──► AES-256-GCM (ключ k1)  ──►  digital_keys (шифротекст, nonce,
            ──► HMAC-отпечаток (f1)         отпечаток, статус)
            admin_import_digital_keys        │
                                             │  оплата (PR3): apply_paid_order проверяет
                                             │  «свободных ключей хватает» (R1)
                                             ▼
                                            fulfillments (pending) ◄── worker: digital_keys_assign
                                             │                          (назначает ключи; секретов нет)
                                             ▼
                                            fulfilled ──► веб: order_delivery_view ──► расшифровка
                                                          (по секрету заказа)          в памяти ──► покупатель
```

| Процесс | Секрет шифрования | Секрет отпечатков | Роль PostgreSQL |
|---|---|---|---|
| веб (`uvicorn api:app`) | да, только для расшифровки | нет | `<prefix>_app` |
| worker выдачи (`python -m commerce.fulfillment_worker`) | **нет** (откажется запускаться, если дан) | нет | `<prefix>_worker` |
| CLI администратора (`python -m commerce.digital_keys.admin`) | да | да | персональная, член `<prefix>_admin` |

### Состояния

- **Ключ:** `available` → `assigned` (навсегда закреплён за позицией заказа) или `available` → `withdrawn` (изъят администратором). Другие переходы запрещены триггером. Удаление и `TRUNCATE` запрещены.
- **Задача выдачи** (`fulfillments`, тип `digital_keys`): `pending` → `fulfilled` (ровно `quantity` назначенных ключей — проверка в базе) или `requires_action` (не хватает ключей, запрошен возврат) или `failed` (ошибки). Вернуть задачу из `requires_action`/`failed` в `pending` и отменить её может только администратор функцией базы. `fulfilled` и `cancelled` — конечные.

### Учёт остатка (R1)

Для товара с `fulfillment_type = 'digital_keys'`:

- `A` — свободные ключи; `W` — оплаченные, ещё не выданные единицы (задачи `pending`/`in_progress`/`requires_action`/`failed`); `Q` — `products.quantity`.
- **Инвариант:** `A ≥ W + Q`.
- **Продаваемый остаток:** `S = max(0, min(Q, A − W))` — представление `product_sellable_stock`. Его показывают каталоги v1/v2; создание заказа проверяет его же.
- **Гарантия — при оплате:** `apply_paid_order` (переопределена в 0004 минимально) под блокировкой строки товара требует `A − W ≥ нужно`. Иначе — прежний путь PR3: деньги учтены, заказ `requires_action`, остаток не списан.
- Повысить `Q` вручную выше `A − W` нельзя (триггер). Понижать — можно. Импорт ключей поднимает `Q` на число новых ключей, но не выше обеспеченного. Изъятие ключа, нарушающее инвариант, отклоняется («сначала уменьшите остаток»).
- Выдача **не** списывает `Q` повторно: остаток списан при оплате (PR3).

**Проверка до оплаты не исключает нехватку после оплаты.** Покупатель видит `S`, но заказ не резервирует товар (так было с PR2): два покупателя могут одновременно оплатить последний ключ. Второй платёж учитывается, заказ уходит в `requires_action`. Кроме того, ключи могут пропасть после оплаты (изъятие в обход учёта, восстановление старой копии). Тогда задача выдачи уходит в `requires_action` с пояснением «Не хватает ключей: нужно N, свободно M». Порядок действий — раздел 6.

## 2. Шифрование и секреты

- **AES-256-GCM** (пакет `cryptography`), nonce 12 случайных байт на каждый ключ.
- **AAD** = `digital-store/key/v1|<product_id>|<public_id>|<enc_key_id>`. Шифротекст нельзя переставить на другой товар, в другую запись или под другую версию ключа: расшифровка такого шифротекста не пройдёт.
- **Отпечаток** = HMAC-SHA256 (отдельный секрет) от ключа после нормализации. Он ищет дубликаты по всей базе. Сам ключ из отпечатка не восстановить.
- **Одна версия секрета отпечатков на склад.** Отпечатки одного кода под разными секретами различаются, поэтому смена секрета отключила бы поиск дубликатов. База отклоняет импорт под версией отпечатков, отличной от версии уже загруженных ключей (любого статуса, включая изъятые). На пустом складе первая версия может быть любой зарегистрированной. Версии ключа шифрования (AES-GCM) меняются независимо.
- **Нормализация:** убираются BOM, CR/LF и пробелы/табуляции по краям. Регистр сохраняется. Запрещены управляющие и невидимые символы. Длина — до 512 символов.
- **Строки файла импорта** разделяются только окончаниями CRLF, LF и CR. Символы, которые Python считает разрывом строки (U+2028, U+2029, U+0085, VT, FF, FS/GS/RS), внутри кода не делят его на два: строка отклоняется вместе со всей партией.
- **Версии:** `DIGITAL_KEYS_ENCRYPTION_KEYS="k1:<base64>,k2:<base64>"`, новые ключи шифруются версией `DIGITAL_KEYS_ACTIVE_KEY`. В каждой записи хранится `enc_key_id`, поэтому старые записи читаются старой версией.
- **Реестр проверочных значений** (`encryption_key_registry`): для каждой версии хранится KCV — первые 16 байт HMAC-SHA256(секрет, `digital-store/kcv/v1/<назначение>/<id>`). Самих секретов в базе нет.
  - CLI импорта сверяет свой секрет с реестром **до** шифрования.
  - Веб сверяет свой секрет с реестром **до** расшифровки.
  - Тот же id с другим секретом → отказ, а не «мусор» в базе.
- Секреты читаются из окружения процесса или из отдельного файла `DIGITAL_KEYS_SECRETS_FILE` (формат `.env`). Отдельный файл нужен, чтобы секреты не лежали в общем `.env`, который читает и worker.
- Ни сообщения об ошибках, ни логи, ни `audit_log`, ни `status_note`/`last_error` не содержат значений ключей или секретов. Это проверяется тестами.

### Создание секретов (один раз)

```powershell
.\.venv\Scripts\python.exe -m commerce.digital_keys.admin generate-key --id k1   # ключ шифрования
.\.venv\Scripts\python.exe -m commerce.digital_keys.admin generate-key --id f1   # секрет отпечатков
```

Выводы команд сохранить в файл секретов. Например, `C:\secure\digital-keys.env` с доступом только у учётной записи веб-сервиса и администратора:

```text
DIGITAL_KEYS_ENCRYPTION_KEYS=k1:...
DIGITAL_KEYS_ACTIVE_KEY=k1
DIGITAL_KEYS_FINGERPRINT_KEY=f1:...
```

Веб-процессу можно дать отдельный файл только с `DIGITAL_KEYS_ENCRYPTION_KEYS`. Затем зарегистрировать версии в базе:

```powershell
$env:DIGITAL_KEYS_SECRETS_FILE = "C:\secure\digital-keys.env"
$env:ADMIN_DB_USER = "ivan_admin"          # персональная учётная запись (раздел 5)
.\.venv\Scripts\python.exe -m commerce.digital_keys.admin verify-keyring --register
```

## 3. Резервная копия и восстановление (R9)

Нужны **две независимые копии**:

1. **База** — `pg_dump -Fc`, как обычно (`DB_ROLES.md`, шаг 1). Шифротексты без секрета бесполезны, поэтому дамп не раскрывает ключи товара. Метаданные (сколько ключей, кому выданы) в дампе есть — храните его как конфиденциальный.
2. **Секреты** — содержимое файла секретов, все версии, которые когда-либо были активными. Минимум две копии вне сервера: менеджер паролей и запечатанная копия на носителе. Не в Git, не в архивах проекта, не рядом с дампом.

**Потеря секрета шифрования = потеря всех ключей, зашифрованных этой версией.** Восстановить их нельзя.

**Восстановление:**

1. `pg_restore` в новую базу.
2. Вернуть файл секретов.
3. Выполнить `verify-keyring`: сверяет каждую версию с реестром и расшифровывает образец ключа каждой версии, загруженной в базу. Значения не печатаются.
4. Только после этого запускать веб и worker.

Репетиция в песочнице проверила `pg_dump` → `pg_restore` в отдельную `*_test` базу. После восстановления выдача вернула те же ключи, а с чужим секретом — 503.

**Ротация.** Добавить `k2` в `DIGITAL_KEYS_ENCRYPTION_KEYS`, сделать `DIGITAL_KEYS_ACTIVE_KEY=k2` и выполнить `verify-keyring --register`. Старые записи читаются `k1`, поэтому `k1` из настройки не убирать. Команды перешифровки старых записей в PR5 нет (формат к ней готов). **Секрет отпечатков сменить нельзя**, пока на складе есть ключи: база отклонит импорт под новой версией. Полная ротация (пересчёт всех отпечатков с расшифровкой) — после PR5.

## 4. Worker выдачи

```powershell
# окружение worker: DB_USER=<prefix>_worker, FULFILLMENT_MODULES=digital_keys; DIGITAL_KEYS_* НЕ задавать
.\.venv\Scripts\python.exe -m commerce.fulfillment_worker --interval 10
.\.venv\Scripts\python.exe -m commerce.fulfillment_worker --once      # один проход
```

- Worker отказывается запускаться, если в его окружении есть любая из `DIGITAL_KEYS_ENCRYPTION_KEYS`, `DIGITAL_KEYS_ACTIVE_KEY`, `DIGITAL_KEYS_FINGERPRINT_KEY`, `DIGITAL_KEYS_SECRETS_FILE` — в том числе подхваченная из общего `.env`. Поэтому, если веб и worker запускаются из одной папки, **не кладите эти переменные в `.env`**. Задайте путь к файлу секретов только веб-процессу:

  ```powershell
  # окно веб-сервера
  $env:DIGITAL_KEYS_SECRETS_FILE = "C:\secure\digital-keys-web.env"   # только DIGITAL_KEYS_ENCRYPTION_KEYS
  .\.venv\Scripts\python.exe -m uvicorn api:app
  ```
- Без `FULFILLMENT_MODULES` ничего не выдаётся: задачи остаются `pending`, как до PR5.
- Задача захватывается `FOR UPDATE SKIP LOCKED`. Ключи назначает функция базы `digital_keys_assign` в транзакции и `SAVEPOINT` worker. Сбой до `COMMIT` возвращает ключи в `available`.
- Если модуль сообщил «выполнено», а база это отклонила (например, ключи не назначены), попытка откатывается целиком и учитывается как неудачная. Worker не падает.
- Можно запускать несколько экземпляров.

## 5. Права администратора (R8)

Административные функции (`admin_import_digital_keys`, `admin_withdraw_digital_key`, `admin_resume_fulfillment`, `admin_cancel_fulfillment`, `admin_reconcile_digital_stock`, `admin_register_encryption_key`, `admin_digital_keys_keyring_sample`, `admin_whoami`) — `SECURITY DEFINER`, `EXECUTE` у `PUBLIC` отозван. Каждая **в базе** вызывает `shop_require_admin`. Ни одна проверка не опирается на имя или префикс роли. Проверки:

1. Группа администраторов задана в `shop_security_settings` (заполняет вывод `db_roles.py --part grants`) и не может входить сама (NOLOGIN).
2. Вошедший — `session_user`, которого `SET ROLE` не меняет — не суперпользователь и не владелец схемы (мигратор).
3. Вошедший — член группы **с наследованием прав**: `pg_has_role(session_user, группа, 'USAGE')`.
4. У вошедшего есть `EXECUTE` на вызываемую функцию.

Права через `PUBLIC`, явно выданный посторонней роли `EXECUTE`, членство без наследования, `SET ROLE` в группу — всё это отклоняется (есть тесты). Проверка в CLI — только для понятного сообщения.

**Персональная учётная запись администратора:**

```powershell
.\.venv\Scripts\python.exe deploy\db_roles.py --prefix digital_store --part admin-login --login ivan_admin > admin_login.sql
& $psql -U postgres -d <база> -v ON_ERROR_STOP=1 -f admin_login.sql
& $psql -U postgres -d <база> -c "\password ivan_admin"
```

`GRANT … WITH INHERIT TRUE, SET FALSE` требует PostgreSQL 16+ (у вас 18). Для 15 и ниже — `GRANT <prefix>_admin TO ivan_admin;` при `INHERIT` у роли.

**Аварийный доступ.** Мигратор и суперпользователь административные функции вызвать не могут — это намеренно. Если администратора нет (утерян пароль, человек ушёл):

1. Под `postgres` создать **временную персональную** роль: `--part admin-login --login emergency_<дата>`, задать пароль.
2. Выполнить нужные действия CLI под ней. В `audit_log` и `imported_by` будет её имя.
3. Удалить роль: `DROP ROLE emergency_<дата>;` (после `REASSIGN`/`DROP OWNED`, если она что-то создала — обычно ничего).
4. Записать в журнал эксплуатации, кто, когда и зачем.

Технически владелец схемы и суперпользователь могут обойти любые проверки: отключить триггеры, вызвать «ядро» функций напрямую. Права PostgreSQL защищают от ролей приложения, worker и посторонних, но не от владельца. Поэтому пароли мигратора и `postgres` не хранятся у приложения.

## 6. Эксплуатация

```powershell
$env:ADMIN_DB_USER = "ivan_admin"; $env:DIGITAL_KEYS_SECRETS_FILE = "C:\secure\digital-keys.env"
$adm = ".\.venv\Scripts\python.exe -m commerce.digital_keys.admin"
```

| Задача | Команда |
|---|---|
| Загрузить ключи (UTF-8, один ключ на строку) | `import-keys --product 7 --file keys.txt --label "Поставщик, счёт 123"` |
| То же, пропустив повторы | `… --skip-duplicates` (иначе партия с повтором отклоняется целиком; в отчёте — номера строк) |
| Запас | `stock [--product 7]` — `Q`, `A`, назначено, изъято, `W`, `A − W − Q` (отрицательное — остаток не обеспечен) |
| Задачи, требующие внимания | `issues` |
| Возобновить после пополнения | `resume --fulfillment 15 --reason "загружено 10 ключей"` (отклоняется, пока свободных ключей меньше нужного) |
| Снять остановку из-за запроса возврата | `resume --fulfillment 15 --reason "возврат отозван" --release-refund-hold` |
| Отменить выдачу (остаток и учёт денег не меняются) | `cancel --fulfillment 15 --reason "возврат клиенту"`; деньги — отдельно `request_refund` (PAYMENTS.md) |
| Изъять скомпрометированный свободный ключ | `withdraw --key <UUID> --reason "…"` (UUID — в `digital_keys.public_id`, видит администратор) |
| Привести остаток к обеспеченному | `reconcile-stock --product 7` (только уменьшает) |
| Проверить секреты | `verify-keyring` |

**Нехватка ключей после оплаты.** Позиция в `issues` со статусом `requires_action`. Покупатель видит `delayed`. Варианты действий:

- загрузить ключи и выполнить `resume`;
- `cancel` и вернуть деньги (`request_refund`).

**Заказ `requires_action` из-за нехватки при оплате.** Сначала загрузить ключи, затем `SELECT admin_retry_paid_order(<id>)` (PR3) — или вернуть деньги.

**Запрос возврата** (`request_refund`) по платежу, который оплатил заказ, автоматически останавливает ещё не выданные ключи (`requires_action`, «Выдача остановлена: запрошен возврат»). Возврат лишнего (повторного) платежа выдачу не останавливает. Уже выданные ключи не отзываются.

**Старые товары с `Q > 0` без ключей** (до PR5): после миграции у них `S = 0`, продажа автоматически останавливается. Можно загрузить ключи (`Q` при этом не растёт выше обеспеченного) или выполнить `reconcile-stock`. Миграция сама старые данные не меняет.

## 7. Блокировки

Глобальный порядок во всех путях:

`fulfillments` → `payments` → `orders` → `products` (по id) → `advisory(импорт)` → `advisory(товар)` → `digital_keys` (по id)

| Путь | Блокировки |
|---|---|
| оплата (`payment_record_provider_state` → `apply_paid_order`) | платёж → заказ → товары `FOR UPDATE` по id |
| выдача (`digital_keys_assign`) | задача → успешный платёж `FOR SHARE` → advisory → ключи `ORDER BY id LIMIT n FOR UPDATE` |
| импорт | товар `FOR UPDATE` → глобальная advisory-блокировка импорта (импорты выполняются по очереди: второй видит ключи первого и получает отчёт о дубликате; проверка версии отпечатков не обходится одновременным первым импортом) |
| изъятие | товар → advisory → ключ |
| возобновление | задача → advisory |
| отмена | задача |
| запрос возврата | платёж `FOR UPDATE` |
| ручное изменение `Q` | товар |

- Advisory-блокировка товара выстраивает выдачу и изъятие в очередь. Без неё `LIMIT … FOR UPDATE` после ожидания занятого ключа возвращал бы меньше строк — ложная нехватка. Мутационный тест это ловит.
- CLI выполняет каждое действие в отдельной транзакции. Скрипты, вызывающие несколько административных функций в одной транзакции, должны соблюдать тот же порядок.
- Сторонние модули выдачи (`FulfillmentHandler`) — тоже.

Проверено тестами на настоящем PostgreSQL с независимыми соединениями и управляемым чередованием (ожидание подтверждается по `pg_stat_activity`), а также стресс-тестом. Подробности — `PR5_NOTES.md`.

## 8. Последовательность проверки после установки

1. `python migrate.py status` — 0004 применена, контрольные суммы 0000–0003 не изменились.
2. `verify-keyring` — все версии «совпадает с реестром», образцы расшифрованы.
3. `stock` — нет отрицательного `A − W − Q` у товаров `digital_keys` (или осознанное решение по каждому).
4. Под ролью app: `SELECT * FROM digital_keys` → `permission denied`.
5. Тестовая покупка в тестовом режиме ЮKassa: `processing` → `delivered`, ключ совпадает с загруженным.
6. Worker запущен **без** `DIGITAL_KEYS_*` в окружении.
