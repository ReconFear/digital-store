## 3. Проверка прав PostgreSQL

`tests/test_digital_keys_privileges.py` — настоящие роли с нестандартным префиксом `dst_<случайно>`. Права выданы выводом `deploy/db_roles.py`, всё — во временной схеме.

**Административные функции (R8).** Проверка в базе (`shop_require_admin`): членство вошедшего с наследованием **и** `EXECUTE`.

| Кто вызывает | Результат |
|---|---|
| персональная роль, член группы `…_admin` (INHERIT) | разрешено, в журнале — имя вошедшего |
| роль `app`, роль `worker` (все 8 функций) | `permission denied` |
| посторонняя роль, которой **явно** выдан `EXECUTE`, без членства | отказ «нужна учётная запись администратора» |
| `EXECUTE` выдан `PUBLIC` (по ошибке) — посторонняя роль и `app` | отказ |
| член группы `WITH INHERIT FALSE, SET TRUE`, сделавший `SET ROLE` в группу | отказ (`session_user` не наследует) |
| роль `NOINHERIT` — член группы (и даже с явным `EXECUTE`) | отказ |
| администратор, сделавший `SET ROLE` в группу | разрешено, в журнале по-прежнему его имя |
| владелец схемы (мигратор) | отказ («под владельцем схемы запрещены») |
| суперпользователь (`postgres`) | отказ |
| группа в настройках — LOGIN-роль или настройки нет | отказ всем («не настроена») |
| `has_function_privilege('public', …)` у всех `SECURITY DEFINER` | ни одной |
| `--part admin-login` при любом префиксе | работает; `SET ROLE` в группу запрещён (`SET FALSE`) |

**Прямой доступ:**

- **app:** нет доступа к `digital_keys`, `digital_key_batches`, `encryption_key_registry`, `digital_key_stock`, `fulfillment_issues`, `shop_security_settings`, `digital_keys_assign`, ядрам, `apply_paid_order`. Читает только `product_sellable_stock`.
- **worker:** нет `SELECT`/`UPDATE` ключей; нет `order_delivery_view`; не может изменить `refund_hold_released_at`/`cancel_reason`/`products`. Прямым `UPDATE` не может поставить `fulfilled` без ключей, отменить задачу или вернуть `requires_action` → `pending` (триггер). Может `digital_keys_assign`.
- **admin:** видит учётные столбцы ключей, но не `ciphertext`/`nonce`/`fingerprint`; не может менять ключи и реестр напрямую.
- **CLI под app/worker** → отказ базы.
- Полный путь под ролями (импорт CLI → заказ app → оплата функцией worker → выдача worker → показ app → `stock` CLI) проходит. `imported_by` = персональная роль.

## 4. Конкурентность (настоящий PostgreSQL, независимые соединения)

Каждый тест: A выполняет шаг и держит транзакцию; B — в отдельном потоке. Ожидание B подтверждено по `pg_stat_activity` (`wait_event_type = 'Lock'`, указан `wait_event`). Затем A фиксирует; `lock_timeout` 5 с.

| Сценарий | Ожидание B | Результат |
|---|---|---|
| оплата ∥ импорт ключей | `tuple`/`transactionid` (строка товара) | оплата видит новые ключи → `paid` |
| две оплаты последнего ключа | строка товара | вторая → `out_of_stock` (`requires_action`), инвариант соблюдён |
| оплата ∥ изъятие (оба порядка) | строка товара | оба успешны, инвариант соблюдён |
| ручное повышение `Q` ∥ оплата | строка товара | триггер видит итог оплаты → отказ (`2 > A − W`) |
| выдача ∥ изъятие, выдача первая | `advisory` | изъятие самого «нижнего» ключа отклонено: он уже выдан |
| выдача ∥ изъятие, изъятие первое | `advisory` | выдача берёт следующий ключ — **ложной нехватки нет** |
| два worker на последний ключ | `advisory` | первый `assigned`, второй `insufficient` (need 1, available 0), частичных назначений нет |
| 4 настоящих worker × 6 заказов (12 ключей) | — | все `fulfilled`, 12 разных ключей, у каждой задачи ровно `quantity` |
| обрыв соединения после назначения до `COMMIT` | — | ключи снова `available`, повтор выдаёт |
| выдача ∥ запрос возврата, возврат первый | строка платежа | `refund_hold`, ключи не назначены |
| выдача ∥ запрос возврата, выдача первая | строка платежа (`FOR SHARE`) | ключи выданы, затем возврат записан |
| выдача ∥ отмена, выдача первая | строка задачи | отмена: «выданное не отзывается» |
| выдача ∥ отмена, отмена первая | строка задачи | выдача: `not_pending`, ключей не назначено |
| два возобновления одной задачи | строка задачи | второе отклонено |
| импорт одного кода в два товара | `advisory` (блокировка импорта, rev2) | второй получает отчёт о дубликате |
| импорт под двумя версиями отпечатков одновременно (rev2) | `advisory` | второй отклонён базой |
| **стресс:** 8 потоков × 200 случайных операций, 3 товара (оплата, worker, импорт, изъятие, возврат, отмена, возобновление, ±`Q`, сверка) | — | 5 прогонов (зёрна 1–5): `40P01 = 0`, `lock_timeout = 0`, неожиданных ошибок 0; ≈1000–1080 успешных операций и ≈520–590 штатных отказов на прогон; в конце `A ≥ W + Q` у всех товаров; у `fulfilled` ровно `quantity` ключей, у прочих — 0 |

Схема блокировок (гипотеза REV3) этими тестами подтверждена в данной среде. Взаимоблокировок и нарушений инварианта не найдено.

**Мутационные проверки:** 23 мутации, каждая в копии проекта с пересозданной базой; все пойманы целевыми тестами:

- убрать advisory-блокировку выдачи;
- убрать проверку возврата;
- убрать `FOR SHARE` платежа;
- убрать проверку `fulfilled`;
- убрать проверку владельца в триггере задач;
- убрать проверку секрета в `order_delivery_view`;
- убрать R1 в `apply_paid_order`;
- убрать триггер остатка;
- убрать инвариант изъятия;
- убрать членство в R8;
- заменить `USAGE` на `MEMBER`;
- заменить `session_user` на `current_user`;
- убрать отказ суперпользователю;
- убрать отказ владельцу;
- убрать `product_id` из AAD;
- убрать `public_id` из AAD;
- пропустить сверку реестра при показе;
- пропустить сверку реестра при импорте;

## 5. Найдено и исправлено во время реализации

1. **Представления вызывали функцию `digital_key_stock_counts`.** `EXECUTE` проверялся бы у читающей роли (app), а таблицы ключей ей недоступны. Подзапросы встроены в представления.
2. **Триггер задач выполняется с правами worker.** Подсчёт ключей для проверки `fulfilled` вынесен в `SECURITY DEFINER` `digital_keys_task_complete` (`EXECUTE` — только worker). Проверка «владелец ли текущая роль» сделана без вызова функций.
3. **Триггер защиты партий и реестра** обращался к `NEW.purpose` и у партий (ошибка компиляции выражения). Исправлено вложенными `IF`.
4. **`quantity_added` партии** считался после вставки неизменяемой строки. Теперь считается до вставки.
5. **Worker падал**, если база отклоняла результат модуля (`fulfilled` без ключей). Теперь попытка откатывается целиком и учитывается как неудачная.
6. **В тестах конкурентности** упавшая проверка оставляла поток B на заблокированном соединении. Добавлено завершение своих сеансов в teardown.

**Отклонение от REV3:** расшифровка выполняется **до** `COMMIT` транзакции показа, в памяти, без дополнительных блокировок. Причина: при ошибке запись `digital_keys.revealed` откатывается и не утверждает, что ключи показаны. Ключ шифрования в базу по-прежнему не передаётся.

## 6. Известные ограничения

- Проверено только в Linux-песочнице с PostgreSQL 16 и тестовой прокладкой вместо psycopg 3. На Windows, Python 3.14, PostgreSQL 18 и с настоящим psycopg не запускалось. Не проверена установка колеса `cryptography==50.0.1` под Windows / Python 3.14 (ожидается abi3-колесо `cp311+`). Тесты FastAPI (включая `test_api_delivery.py`) не запускались.
- Заказ не резервирует товар (как с PR2). Проверка при создании заказа — подсказка: нехватка после оплаты возможна (параллельные оплаты, пропажа ключей). Она безопасно уходит в `requires_action` с процедурой администратора, но **не исключена**.
- Веб-процесс держит секрет шифрования: компрометация веб-сервера раскрывает выданные и невыданные ключи. Права базы этого не закрывают.
- Владелец схемы и суперпользователь технически могут обойти проверки (отключить триггеры, вызвать ядра). R8 защищает от ролей приложения, worker и посторонних.
- Нет CLI перешифровки. Секрет отпечатков при непустом складе сменить нельзя: импорт под другой версией база отклоняет (rev2).
- `admin_retry_paid_order` (PR3) не требует персональной учётной записи — права группы, как в PR3.
- `/status` (PR3) для заказа с одной выполненной и одной отменённой позицией показывает `fulfillment_status = in_progress`. Это прежняя логика сводки, не менялась.
- Каталоги считают продаваемый остаток подзапросом на товар — для больших каталогов может понадобиться оптимизация.
- Лимит частоты — в памяти процесса (как в PR3).
- Импорты выполняются строго по очереди (глобальная блокировка импорта, rev2). Проверка версии отпечатков просматривает таблицу ключей при каждом импорте.

## 7. Порядок безопасного применения миграции

Рекомендация — сначала завершить переход на роли (`DB_ROLES.md`) и применять 0004 **мигратором**. Если объекты ещё принадлежат `postgres`, функции `SECURITY DEFINER` 0004 тоже окажутся у суперпользователя; шаг ownership `db_roles.py` (теперь со всеми объектами 0004) это исправляет, но лучше не допускать.

1. **Резервная копия:** `pg_dump -Fc -f before_pr5.dump digital_store`. Дамп — не в Git и не в архивы.
2. **Репетиция:**
   - восстановить дамп в отдельную базу (например, `digital_store_pr5_rehearsal_test`);
   - на ней выполнить `migrate.py status` → `migrate.py apply --database … --confirm-database …`;
   - выполнить шаги 5–10;
   - прогнать тесты на тестовой базе.
3. **Остановить** веб-процесс и платёжный обработчик: `ALTER TABLE fulfillments` берёт эксклюзивную блокировку, `apply_paid_order` переопределяется.
4. `python migrate.py status`, затем `apply` под мигратором. Миграция выполняется одной транзакцией; при ошибке ничего не меняется.
5. `python deploy\db_roles.py --part grants` → прочитать → применить. В выводе — права на объекты 0004 и запись группы администраторов.
6. `--part admin-login --login <имя>` → применить → `\password <имя>`.
7. Создать секреты (`generate-key --id k1`, `--id f1`), записать их в файл секретов и **в две резервные копии вне сервера**.
8. `verify-keyring --register` под персональной ролью.
9. `stock` — решить по каждому старому товару `digital_keys` с `A − W − Q < 0`: загрузить ключи или `reconcile-stock`. До решения они не продаются (`S = 0`).
10. Запустить веб (с `DIGITAL_KEYS_SECRETS_FILE` только в его окружении) и платёжный обработчик. Затем запустить worker выдачи: роль worker, `FULFILLMENT_MODULES=digital_keys`, без `DIGITAL_KEYS_*`.
11. Тестовая покупка в тестовом режиме ЮKassa и проверка по `DIGITAL_KEYS.md`, раздел 8.

**Откат:** сама 0004 не удаляет данных. Для отката до 0003 — `pg_restore` дампа шага 1. Ключи, загруженные после миграции, при этом теряются; их надо выгрузить заранее, если откат вероятен.

## 8. API-контракт для Артёма

Полностью — `FRONTEND_DELIVERY_API.md`. Кратко:

- **Запрос:** `POST /api/v2/orders/{order_id}/delivery`, тело `{"access_token": "…"}`.
- **Ответ 200:** `{order_id, order_status, items[]}`. Элемент `items[]`: `{order_item_id, product_id, name, fulfillment_type, quantity, delivery_status, digital_keys?}`.
- **`delivery_status`:** `awaiting_payment`, `processing`, `delivered`, `delayed`, `cancelled`, `manual`, `not_applicable`. Поле `digital_keys` есть только при `delivered`.
- **Ошибки:** `404 order_not_found` (неверный секрет и несуществующий заказ неотличимы), `422`, `429 rate_limited` (20/мин, `Retry-After`), `503 delivery_unavailable`.
- **Заголовки:** у всех ответов маршрута — `Cache-Control: no-store`, `Pragma: no-cache`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
