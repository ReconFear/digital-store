# PR 2 rev3-fix — обход целостности через временную схему `pg_temp`

Основа — PR 2 rev3. Исправления rev2 и rev3 сохранены полностью. Python-ядро, API v1/v2, JS-клиент и витрина не менялись. `0000`/`0001` не менялись. Изменена только `0002` (у вас ещё нигде не применялась), отдельная `0003` не нужна.

## 1. Суть проблемы

Триггерные функции 0002 обращаются к таблицам `orders`, `order_items`, `products` без имени схемы. В rev3 им задавался путь `SET search_path FROM CURRENT`. В рабочей базе это `"$user", public`, во временных тестовых схемах — `ds_mig_*`.

Если `pg_temp` не указан в пути **явно**, PostgreSQL ищет временную схему сессии **первой**. Значит, любая сессия может выполнить `CREATE TEMP TABLE orders (...)`, и проверки в триггерах прочитают поддельную таблицу вместо настоящей.

## 2. Воспроизведение на настоящем PostgreSQL 16.15 (база из rev3, схема `public`, роль без прав суперпользователя)

В функциях rev3: `search_path="$user", public`.

| # | Что сделано в сессии | Результат на rev3 |
|---|---|---|
| 1 | `CREATE TEMP TABLE orders` со строкой `(1, 'RUB', 99900, items_sealed = FALSE)`, затем `INSERT INTO public.order_items` в закрытый заказ №1 | **позиция добавлена**: в заказе №1 стало 2 позиции |
| 2 | `SET LOCAL allow_history_delete = 'on'`, `CREATE TEMP TABLE order_items` с поддельной строкой `(1, 99900, 'RUB')`, `DELETE FROM public.order_items WHERE order_id = 1`, `COMMIT` | **COMMIT прошёл**: заказ №1 существует, позиций 0 |
| 3 | `CREATE TEMP TABLE orders` с поддельной строкой для id = 2, затем `INSERT INTO public.orders (product_id, price)` | закрытие ушло во временную таблицу: настоящий заказ №2 **`items_sealed = false`**, его можно дополнять |
| 4 *(найден дополнительно)* | `CREATE TEMP TABLE products` с `(1, 'ПОДДЕЛКА', ...)`, затем `INSERT INTO public.orders (product_id, price)` | снимок товара в позиции заказа v1 — **«ПОДДЕЛКА»** |

Все четыре обхода подтверждены.

## 3. Исправление

Новый блок «5б. доверенный search_path триггерных функций» в `0002`. Тот же блок есть в `schema.sql`.

```sql
DO $$
DECLARE
    shop_schema TEXT := current_schema();
    fn TEXT;
BEGIN
    IF shop_schema IS NULL OR shop_schema LIKE 'pg\_temp%' OR shop_schema = 'pg_catalog' THEN
        RAISE EXCEPTION 'миграция должна выполняться со схемой магазина в search_path (сейчас: %)', shop_schema;
    END IF;
    FOREACH fn IN ARRAY ARRAY[ ...10 триггерных функций... ] LOOP
        EXECUTE format('ALTER FUNCTION %I.%I() SET search_path = pg_catalog, %I, pg_temp',
                       shop_schema, fn, shop_schema);
    END LOOP;
END
$$;
```

Почему так:

- **`pg_temp` явно последний.** Временные таблицы ищутся только после настоящих и подменить их не могут.
- **`pg_catalog` первый.** Встроенные функции и операторы нельзя подменить объектами в схеме магазина.
- **`"$user"` убран.** Закрыт и риск «схема с именем пользователя раньше `public`», отмеченный в rev3.
- **Схема берётся из `current_schema()` в момент миграции.** Одинаково работает в `public` (рабочая и тестовая базы) и во временных схемах `ds_mig_*` (тесты миграций). Явные имена схем в теле функций сделали бы функции привязанными к `public`, и тесты в схемах `ds_mig_*` перестали бы проверять настоящий код.
- **Путь хранится в функции буквально** (`SET search_path TO 'pg_catalog', 'public', 'pg_temp'`) и переносится `pg_dump`.
- **Применяется к явному списку из 10 функций магазина**, а не ко всем функциям схемы: функции расширений в `public` не затрагиваются.

`SET search_path FROM CURRENT` из объявлений функций удалён.

| `test_trigger_functions_have_trusted_search_path_in_public` | То же в `public` тестовой базы, установленной `migrate.py` |

Каждая атака выполняется в **отдельном новом соединении** — как у настоящего атакующего.

**Важная находка при написании тестов.** В первой версии атаки шли в той же сессии, где функции уже выполнялись. PL/pgSQL использовал план, закэшированный до появления временной таблицы, и в одном сценарии уязвимая конфигурация выглядела защищённой. Создание временной таблицы не сбрасывает кэш планов. В свежей сессии атакующего кэша нет, поэтому тесты переведены на отдельные соединения. Исправление от кэша не зависит: путь закреплён в самой функции.

## 9. Оставшиеся риски (без изменений с rev3, кроме закрытого)

- **Права доступа.** Триггеры не защищают от владельца таблиц: он может изменить или отключить функцию, в том числе её `search_path`. Нужна отдельная роль приложения без владения таблицами и без `DELETE`/`TRUNCATE`.
- **Ручной `UPDATE` в `paid`** без списания остатка возможен для того, у кого есть права на `UPDATE`. Ограничивать правами вместе с платёжным провайдером.
- **Python-код приложения** выполняет запросы без имени схемы в своих соединениях. Временные таблицы в них создаёт только само приложение (оно этого не делает), поэтому подмена там возможна лишь при выполнении чужого SQL в сессии приложения — что уже означает компрометацию.
- `pg_restore --data-only` в готовую схему не поддерживается; возвраты и отмена оплаченных заказов не реализованы; единицы цен в `digital_store` не подтверждены.
