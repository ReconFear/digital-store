# PR 3 rev2 — платёжная конкурентность и неопределённые операции

Основа — `digital-store-pr3.zip`. Миграции `0000`–`0002` не изменены ни на байт (сверено с архивом PR 3 и тестом контрольных сумм). Изменена только `0003` (на Windows ещё не применялась), `schema.sql` пересобран. API v1/v2, JS-клиент, витрина, заказы, fulfillment и исправления PR 2 сохранены. Основная база `digital_store` не использовалась.

## 1. Гонка в очереди уведомлений — исправлено

**Было.** Повторный webhook делал `next_attempt_at = LEAST(…, now())` для событий в `received`/`failed`. Захваченное событие помечалось только сдвигом `next_attempt_at` вперёд (статус оставался `received`), поэтому повторная доставка могла «освободить» его во время обработки, второй обработчик брал его параллельно, а итог записывался без проверки, чей он.

**Стало** (`provider_events`, `payments/service.py`, PAYMENTS.md §5б):

| Требование | Реализация |
|---|---|
| Явное состояние обработки | статус `processing`; ограничение `provider_events_lease_check`: `processing` ⇔ заданы `lease_token` и `lease_expires_at` |
| Идентификатор аренды | `lease_token UUID` — новый при каждом захвате (`gen_random_uuid()`) |
| Условное завершение и ошибка | `UPDATE … WHERE id = … AND status = 'processing' AND lease_token = <свой>`; не совпало — `stale_lease`, ничего не записано |
| Повторный webhook не освобождает аренду | `provider_event_accept`: при `processing` аренда и `next_attempt_at` не меняются, ставится `recheck_requested`; после завершения событие возвращается в `received` и перепроверяется у провайдера. Для `failed` пауза повтора тоже больше не сбрасывается |
| После аварии задача доступна | захват берёт `received`/`failed` с наступившим сроком **или** `processing` с истёкшей арендой (5 минут) |
| Устаревший обработчик не меняет результат нового | проверено, когда новый уже закончил и когда новый ещё работает |

Сам учёт оплаты по-прежнему идемпотентен (блокировка строки платежа и заказа, уникальные индексы), поэтому даже одновременная обработка одного платежа двумя обработчиками не даёт двойного списания. Аренда защищает итоговую запись события.

## 2. Неизвестный результат после 23 часов — исправлено

**Было.** Попытка `creating`/`unknown` старше 23 часов становилась `requires_action` (`stale_attempt`), и следующий checkout создавал новую попытку с новым ключом. Если старый платёж потом оплачивали, получались две реальные оплаты одного заказа.

**Стало** (PAYMENTS.md §5а):

1. Старше 23 часов — `requires_action` / `unresolved_attempt`. Повтор со старым ключом не делается.
2. **Любая `requires_action` без решения блокирует новые попытки заказа**: `payment_attempt_start` возвращает `payment_under_review`, API отвечает 409, ссылка не выдаётся, к провайдеру ничего не уходит. Это проверяется в функции БД, а не только в Python.
3. Сверка ищет платёж в списке платежей магазина (`GET /v3/payments`, `created_at.gte`/`created_at.lt`, все страницы по `next_cursor`, совпадение `metadata.payment_attempt` и `metadata.order_id`). Формат запроса сверен с официальным SDK ЮKassa (yookassa-sdk-python, `docs/examples/02-payments.md`) и страницей «Работа со списками».
   - Найден — попытка продолжает обычную обработку с полной сверкой; оплачен — заказ проводится один раз. Единственный разрешённый выход из `requires_action` — `unresolved_attempt` без решения и без учтённых денег.
   - Не найден — **не доказательство**: попытка остаётся `requires_action`, поиск повторяется раз в час 35 дней.
   - Список просмотрен не целиком — вывода нет.
4. Решение человека — `admin_resolve_payment(id, 'not_paid_confirmed' | 'handled_manually', 'основание')`. Обязательно основание; `not_paid_confirmed` невозможно, если по попытке учтены деньги. После решения оплата снова доступна, покупатель видит `payment_status = canceled`.
5. Поздние деньги по уже разрешённой попытке учитываются (`late_success_recorded`): создаётся запрос возврата, решение снимается (`status_reason = late_payment`), всё пишется в `audit_log`. Повторные события по ней больше ничего не делают.

Автоматически «потерянную» попытку система не закрывает никогда. Состояние честно показывается как `requires_action`.

## 3. Проверка ответа на создание — исправлено

До выдачи `confirmation_url` (`_create_response_problem` в `service.py`) проверяются:

| Проверка | Причина при несовпадении |
|---|---|
| `metadata.order_id` и `metadata.payment_attempt` | `create_response_mismatch:metadata` |
| сумма и валюта | `…:amount` |
| `recipient.account_id` = shopId | `…:shop` |
| `test` = режим магазина | `…:test_mode` |
| `status` согласован с `paid` | `…:status_paid` |
| для `pending`: ссылка `https://`, без логина/пароля, порт 443, домен из `YOOKASSA_CONFIRMATION_HOSTS` (по умолчанию `yoomoney.ru`, `yookassa.ru` и их поддомены) | `…:confirmation_url` |
| ID платежа совпадает с уже привязанным к попытке | `payment_checkout_bind` → `id_conflict`, ссылки нет, запись в журнале |

При любом расхождении ссылка не выдаётся, попытка не привязывается и становится `requires_action`; новые попытки заказа заблокированы до решения человека. Согласованный ответ со статусом не `pending` даёт `confirmation_url: null`. Та же проверка `status`/`paid` добавлена в обработчик (`provider_state_inconsistent`). Адаптер больше не отбрасывает ссылку молча: решение о допустимости принимает сервис.

## 4. Права PostgreSQL — сокращены

| Роль | Было | Стало |
|---|---|---|
| `app` | `SELECT` на `order_access`, `payments`, `refunds`, `fulfillments`; `INSERT` на `order_access`; `SELECT/INSERT/UPDATE` на `provider_events`; `EXECUTE` на `payment_attempt_bind/mark` (любая попытка) | `SELECT` только `products`, `orders`, `order_items` (нужно для `RETURNING` и триггеров 0002); `INSERT` `orders`, `order_items`. Всё остальное — через функции, требующие SHA-256 секрета заказа: `order_access_issue` (только заказ, создаваемый в этой транзакции), `order_status_view`, `payment_attempt_start`, `payment_checkout_bind`, `payment_checkout_mark`, `provider_event_accept` |
| `worker` | `SELECT` на `money_operations`, `refunds`; `UPDATE` на `provider_events` целиком | `SELECT` `payments`, `provider_events`, заказы, товары, `fulfillments`; `UPDATE` только столбцов статуса и аренды событий; `EXECUTE` `payment_attempt_bind/mark/touch`, `payment_record_provider_state` |
| `admin` | `SELECT` всего | всего, кроме `order_access` (хэши секретов); `+ admin_resolve_payment` |

Веб-роль с секретом одного заказа не может привязать, пометить или увидеть попытку другого заказа: функции возвращают `not_found`, попытка не меняется. Роли пользователя не создаются и не меняются: `deploy/db_roles.py` только печатает SQL.

## 7. Ограничения (без изменений, кроме закрытых)

Закрыто в rev2: гонка очереди, повторная оплата после истечения ключа, выдача ссылки по противоречивому ответу, чтение платёжных таблиц веб-ролью.

Остаётся:
- возвраты не исполняются через API;
- нет чеков 54-ФЗ и двухстадийной оплаты;
- лимит частоты хранится в памяти процесса;
- нет админ-интерфейса (решения — SQL-функциями);
- поиск «потерянной» попытки ограничен 5000 платежами в окне (иначе «нет вывода»);
- доверие к процессу-обработчику (ЮKassa не подписывает уведомления);
- единицы цен в `digital_store` не подтверждены.

**Блокировка новых попыток требует работы человека**: если ЮKassa сутки не отвечает на создание платежа, заказ нельзя оплатить, пока администратор не разрешит попытку или сверка не найдёт платёж. Это сознательный выбор в пользу защиты от двойного списания.
