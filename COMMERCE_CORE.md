# Digital Store — универсальное коммерческое ядро (PR 2)

Документ для backend-разработчиков: как устроены товары, деньги, заказы, оплата и исполнение. Контракт API для frontend — в [`FRONTEND_API.md`](FRONTEND_API.md), инструкция для Артёма — в [`FRONTEND_INTEGRATION.md`](FRONTEND_INTEGRATION.md).

## 1. Общая схема

Модульный монолит: одно приложение FastAPI, одна база PostgreSQL на магазин (клиента).

```text
api.py                  HTTP: v1 (старый контракт) + v2 (/api/v2/...)
database.py             v1: каталог и заказ одного товара (контракт не менялся)
commerce/
  money.py              денежная модель и границы сумм
  catalog.py            каталог v2
  orders.py             создание многопозиционного заказа
  schemas.py            схемы запросов и ответов v2 (pydantic)
  fulfillment.py        контракт модулей исполнения + обработчик задач
payment_service.py      применение ПОДТВЕРЖДЁННОЙ оплаты (без публичного API)
migrations/0002_...     схема ядра и перенос старых данных
```

Жизненный цикл покупки и где что происходит:

| Этап | Где | Статус в PR 2 |
|---|---|---|
| Каталог | `GET /products` (v1), `GET /api/v2/products` | готово |
| Корзина | в браузере (localStorage и т. п.) | на стороне frontend; сервер корзину не хранит |
| Заказ | `POST /orders` (v1, один товар), `POST /api/v2/orders` (несколько позиций) | готово: `pending`, цены и итог считает сервер |
| Резерв товара | — | **нет** (см. раздел 6) |
| Оплата у провайдера | — | **нет**: следующий этап (создание платежа, webhook, проверка подписи) |
| Применение подтверждённой оплаты | `payment_service.apply_verified_payment` | готово: списание остатков, `paid`, задачи исполнения |
| Исполнение | `commerce/fulfillment.py` | готов контракт и обработчик задач; модулей выдачи **нет** |
| Отмена, возврат | — | **нет** |

## 2. Товар: три независимых признака

| Колонка | Значения | Смысл |
|---|---|---|
| `product_type` | `digital_key`, `digital_file`, `physical`, `service`, `other` | что продаётся (для витрины и отчётов) |
| `inventory_mode` | `tracked`, `unlimited` | учитывается ли остаток `quantity` |
| `fulfillment_type` | `manual`, `digital_keys`, `downloads`, `physical_shipping` | какой модуль исполняет заказ после оплаты |

Допустимые сочетания закреплены в базе (`products_type_combination_check`):

| `product_type` | `inventory_mode` | `fulfillment_type` |
|---|---|---|
| `digital_key` | только `tracked` (ключей конечное число) | `digital_keys` или `manual` |
| `digital_file` | любой (`unlimited` — продаётся сколько угодно раз) | `downloads` или `manual` |
| `physical` | только `tracked` | `physical_shipping` или `manual` |
| `service` | любой (`tracked` — ограниченное число мест) | `manual` (задача исполнителю; это и есть «manual_service») |
| `other` | любой | `manual` |

У `unlimited`-товара `quantity` всегда 0: остаток не используется (`products_unlimited_quantity_check`).

**Старые товары** после миграции: `other` + `tracked` + `manual`. Тип не угадывается по названию, поведение прежнее. Переклассифицировать товар можно обычным `UPDATE` (будущая админка). Пример:

```sql
UPDATE products SET product_type = 'digital_key', fulfillment_type = 'digital_keys' WHERE id = 1;
```

## 3. Деньги

- Все суммы — **целые числа в минимальных единицах** (копейки для RUB): `BIGINT` в базе, `int` в Python, целые `number` в JSON. `float` не используется нигде.
- Валюта хранится рядом с каждой суммой: `products.currency`, `orders.currency`, `order_items.currency`.
- Поддерживаемые валюты — `commerce/money.py: CURRENCY_EXPONENTS` (сейчас только `RUB`, 2 знака). Товар в другой валюте можно сохранить в базе, но он не показывается в каталоге v2 и не продаётся, пока валюта не добавлена в список. Добавление валюты = строка в этом словаре плюс проверка налогов и округлений для неё.
- Один заказ — одна валюта. Смешивание отклоняется (`mixed_currency`).
- Границы (переполнение невозможно ни в PostgreSQL, ни в JavaScript):

| Величина | Предел |
|---|---|
| цена единицы | ≤ 10¹² минимальных единиц (10 млрд ₽) — CHECK в базе |
| количество в позиции | 1…1000 — CHECK в базе и схема API |
| позиций в заказе | ≤ 50 — схема API |
| итог заказа | ≤ 10¹⁵ — проверка в `money.order_total_minor` (меньше 2⁵³) |

- `line_total_minor = unit_price_minor × quantity` закреплено CHECK в `order_items`.

### Старое поле `price` (целые рубли)

`products.price` и `orders.price` остаются для совместимости с API v1, `seed.sql` и старыми SQL-скриптами:

- главная цена — `price_minor`; `price` — её зеркало в целых рублях;
- триггер `products_sync_legacy_price`: если записан только `price`, то `price_minor = price × 100` (только RUB); если записан `price_minor`, то `price = price_minor / 100` для RUB без копеек, иначе `NULL`;
- `products_legacy_price_check` гарантирует согласованность обоих полей.

Товары с `price = NULL` (копейки, другая валюта) и `unlimited`-товары **не видны в API v1**: его формат (`price` в целых рублях, целый `quantity`) их честно не описывает. Все товары, созданные до PR 2, видны в v1 как раньше.

## 4. Заказ

```text
orders        id, status, currency, total_minor, created_at, paid_at, items_sealed,
              product_id, price            ← только у заказов v1, у заказов v2 — NULL
order_items   order_id, product_id, product_name, product_type, fulfillment_type,
              quantity, unit_price_minor, currency, line_total_minor   (снимок на момент заказа)
```

Правила создания (`commerce/orders.py:create_order`, `POST /api/v2/orders`):

1. Клиент присылает только `product_id` и `quantity`. Лишние поля (`price`, `total`, `status`, `currency`…) → 422.
2. Повторяющиеся `product_id` объединяются (количества складываются); после объединения снова проверяется предел 1000.
3. Нет товара или он снят с продажи → 404 `product_not_found` (с перечнем `product_ids`).
4. Валюты разные → 409 `mixed_currency`; валюта не поддерживается → 409 `unsupported_currency`.
5. `tracked`-товара меньше, чем заказано → 409 `insufficient_stock`. Это проверка на момент заказа, **не резерв**: остаток не уменьшается.
6. Цена, название, тип и способ исполнения каждой позиции копируются в `order_items`. Итоги считаются на сервере.
7. Всё — одна транзакция: при любой ошибке не остаётся ни заказа, ни позиций.

### Целостность заказа (защита на уровне базы)

Транзакционная граница: **заказ и весь его состав создаются в одной транзакции**. При её COMMIT состав проверяется, и заказ закрывается навсегда.

| Что | Как обеспечено |
|---|---|
| Позицию можно добавить только при создании заказа | `orders.items_sealed`: при COMMIT транзакции создания отложенный триггер `orders_check_composition` ставит `TRUE`; `order_items_guard_insert` отклоняет INSERT в закрытый заказ. Другие транзакции незакоммиченный заказ не видят |
| Закрытие нельзя отменить | `orders_protect_history`: `items_sealed` меняется только `FALSE → TRUE` |
| Валюта позиции = валюта заказа | `order_items_guard_insert` |
| У заказа есть позиции, сумма позиций = итог, валюта одна | отложенные до COMMIT проверки `orders_check_composition` на INSERT в `orders`/`order_items` **и на DELETE из `order_items`** |
| Позиции не меняются | `order_items_protect_history` |
| Удаление позиций и заказов | запрещено; осознанное удаление — только с `allow_history_delete` и только **заказа целиком** (иначе COMMIT отклонит) |
| TRUNCATE (в том числе CASCADE) | запрещён всегда, без исключений |
| Товар, цена, валюта, итог заказа не меняются | `orders_protect_history` |

**Почему флаг, а не номер транзакции.** В ревизии 2 использовался `created_txid` — номер транзакции создания. Номера транзакций уникальны только внутри одного кластера PostgreSQL. После `pg_dump`/`pg_restore` в другой кластер (переезд, восстановление из копии) счётчик нового кластера может дойти до сохранённого номера, и тогда транзакция с этим номером дописала бы позицию в старый заказ. Это воспроизведено на двух настоящих кластерах. `items_sealed` — обычные данные: он переносится дампом и ни от каких счётчиков не зависит.

**Резервное копирование и восстановление.**

- **Полный дамп** (`pg_dump` → `pg_restore` в пустую базу) работает: триггеры восстанавливаются после данных, закрытые заказы остаются закрытыми.
- Все триггерные функции имеют закреплённый путь поиска `pg_catalog, <схема магазина>, pg_temp` (блок «5б» миграции 0002). Поэтому они работают и в сессиях `pg_restore`, где `search_path` пустой, и не видят временных таблиц раньше настоящих: без явного `pg_temp` в конце PostgreSQL ищет временную схему сессии **первой**, и `CREATE TEMP TABLE orders` подменил бы данные проверок (воспроизведено, см. `PR2_NOTES_REV3_FIX.md`). Путь хранится в функции буквально и переносится `pg_dump`.
- На другой сервер, где нет роли-владельца, восстанавливайте с `pg_restore --no-owner` (или создайте роль заранее).
- **Загрузка только данных** (`--data-only`) в базу, где схема уже создана, не поддерживается: триггеры и внешние ключи активны. Нужно восстанавливать базу целиком.

### Статусы заказа

```text
новый заказ: pending   (legacy — только для исторических записей, инертен)
pending         → paid | requires_action | cancelled
requires_action → paid | cancelled
paid, cancelled, legacy — конечные (возвраты и отмена оплаченных — следующий этап)
```

Охраняет `orders_guard_status`:

- переход в `paid` требует `paid_at`;
- `paid_at` задаётся только в момент перехода в `paid` и больше не меняется (CHECK: `paid_at` есть только у `paid`);
- у исторических оплаченных заказов `paid_at` остаётся `NULL` — время неизвестно, и задать его задним числом нельзя;
- вернуть `paid` в `pending` нельзя. Поэтому повторное подтверждение оплаты всегда даёт `already_paid` и не списывает остаток второй раз.

**Осознанное удаление** — уборка тестовых данных или ручное исправление — только явно, в одной транзакции и только заказом целиком:

```sql
BEGIN;
SET LOCAL digital_store.allow_history_delete = 'on';
DELETE FROM fulfillments WHERE ...; DELETE FROM order_items WHERE ...; DELETE FROM orders WHERE ...;
COMMIT;   -- если остался заказ без позиций или с неверным итогом — COMMIT отклоняется
```

Это защита от ошибок приложения и случайного SQL, а **не от владельца базы**: пользователь с правами на таблицы может выключить триггер. Настоящая граница — права PostgreSQL. На следующем этапе рабочей роли приложения стоит выдать на `orders`/`order_items` только `SELECT, INSERT, UPDATE`, без `DELETE`, `TRUNCATE` и прав владельца.

**Заказ v1** (`POST /orders`) — та же модель. Строка `orders` старого формата автоматически получает валюту, итог и одну позицию (триггеры `orders_fill_legacy_columns`, `orders_create_legacy_item`). Ответ v1 не изменился.

Статусы заказа: `pending` (создан), `paid` (оплата применена), `requires_action` (оплата применена, но выдать нельзя — нужен человек), `cancelled`, `legacy` (заказ из времени до статусов).

**Чтения заказа по HTTP нет намеренно.** `GET /api/v2/orders/{id}` без аутентификации позволил бы перебором `id` видеть чужие заказы. Варианты на следующих этапах: вход покупателя (заказы своего аккаунта) или одноразовый секретный токен заказа (хранится только хеш, передаётся в заголовке, не в URL). До этого клиент получает полный заказ один раз — в ответе на создание.

## 5. Подтверждённая оплата — `payment_service.apply_verified_payment(order_id)`

Вызывать **только** серверным кодом после проверки платежа у провайдера. Публичного API нет, браузер не может сделать заказ оплаченным.

Одна транзакция:

1. `SELECT ... FOR UPDATE` заказа. `paid` → `already_paid` (повтор ничего не меняет). Не `pending`/`requires_action` → `invalid_order_status`.
2. Блокировка всех товаров заказа **в порядке возрастания id**. Во всех транзакциях порядок одинаковый, поэтому взаимных блокировок нет; это проверено тестом с заказами «A, B» и «B, A».
3. Проверка каждой позиции: товар в продаже; для `tracked` хватает остатка.
4. Не хватает хотя бы одной позиции → **остатки не меняются**, заказ получает `requires_action`, ответ `{"error": "out_of_stock", "problems": [...]}`. Деньги получены, а выдать нельзя: решение (дозаказ или возврат) за человеком. После пополнения остатка повторный вызов доведёт заказ до `paid`.
5. Иначе списывает остатки всех `tracked`-позиций условным `UPDATE` (отрицательный остаток невозможен) и ставит `paid` с `paid_at`. Для каждой позиции создаётся задача исполнения `fulfillments` (`pending`), идемпотентно.

Остаток списывается при оплате, а не при создании заказа, как и до PR 2.

**Где появится платёжный провайдер (следующий этап):** таблица платежей (id провайдера, сумма, валюта, статус) и журнал событий webhook (уникальный id события). Webhook проверяет подпись, сумму и валюту против `orders.total_minor/currency` и только затем вызывает `apply_verified_payment`. Возвраты и отмены — отдельные операции над платежом с возвратом остатков; в PR 2 их нет.

## 6. Резервирование — сознательно не сделано

Заказ проверяет остаток, но не держит его. Между заказом и оплатой товар может закончиться. Тогда оплата не теряется: заказ получает `requires_action` (раздел 5). Резерв с TTL требует продуманного жизненного цикла: истечение, освобождение, продление на время оплаты, защита от «скупки» резервов без входа. Делать его стоит вместе с платёжным провайдером, когда известно время жизни платёжной сессии.

## 7. Исполнение — `commerce/fulfillment.py`

- `fulfillments`: одна задача на позицию оплаченного заказа. Статусы: `pending`, `in_progress`, `fulfilled`, `requires_action`, `failed`, `cancelled`. `fulfilled_at` заполнен тогда и только тогда, когда статус `fulfilled` (CHECK).
- Модуль реализует `FulfillmentHandler` (`fulfillment_type`, `fulfill(conn, task) -> FulfillmentResult`) и регистрируется через `register_handler()`.
- `process_pending_fulfillments()` берёт задачи `FOR UPDATE SKIP LOCKED` и вызывает модуль в той же транзакции. За один запуск каждая задача обрабатывается не больше одного раза.
- Транзакционные границы одной попытки:

  ```text
  BEGIN
    SELECT ... FOR UPDATE SKIP LOCKED      -- захват задачи
    SAVEPOINT fulfillment_attempt
      handler.fulfill(conn, task)
    успех:  RELEASE SAVEPOINT; UPDATE статус
    ошибка: ROLLBACK TO SAVEPOINT          -- откат только изменений модуля, блокировка задачи сохраняется
            UPDATE attempts/last_error/next_attempt_at ... WHERE attempts = <прочитанное значение>
  COMMIT                                   -- результат записан и блокировка снята одновременно
  ```

  Конкурирующий воркер не может взять задачу, пока результат попытки не записан. Это работает и для ошибок самой базы (транзакция в состоянии aborted): `ROLLBACK TO SAVEPOINT` возвращает её в рабочее состояние.
- После неудачи задача откладывается: `next_attempt_at = now() + retry_delay_seconds × 2^(попытка−1)`, не больше часа (по умолчанию 30 с, 60 с, 120 с…). До этого времени её не возьмёт ни один воркер.
- Модулю **запрещено** вызывать `conn.commit()` / `conn.rollback()`. Если модуль это сделал, воркер не падает: он заново захватывает задачу только при неизменённом числе попыток и записывает попытку один раз. Изменения, которые модуль успел закоммитить сам, откатить уже нельзя — это нарушение контракта модуля.
- Модуль должен быть **идемпотентным** по `task.id`. Пример: для `digital_keys` — назначить ключ с `UNIQUE(fulfillment_id)`, чтобы повтор не выдал второй.
- Ошибка модуля откатывает его изменения. В задаче сохраняется только имя класса исключения или публичное сообщение `FulfillmentError` — ключи, ссылки и токены в базу ошибок не попадают. После `max_attempts` задача получает `failed`.
- **В PR 2 модулей нет.** Оплаченные позиции остаются `pending` («оплачено, ожидает исполнения»). Ничего не помечается выполненным без реального действия. Модули `digital_keys`, `downloads`, `physical_shipping`, `manual` (с админкой) и периодический запуск обработчика — следующие этапы.

## 8. Миграция 0002

Подробный анализ — в `PR2_NOTES.md`. Кратко:

- старые цены: `price_minor = price × 100`, `RUB`. Основание: старый код печатал `"{price} RUB"`, `FRONTEND_API.md` описывает `price` как целые рубли;
- каждый старый заказ получает одну позицию с **ценой самого заказа** (`orders.price`), а не текущей ценой товара;
- `created_at` старых заказов остаётся `NULL`, задачи исполнения для старых оплаченных заказов не создаются: историю не придумываем;
- в конце миграции — проверка: цены, позиции и итоги сходятся. Иначе откатывается весь запуск;
- чистая установка и обновление дают одинаковую схему (тест `test_fresh_install_equals_upgrade`, сверка `schema.sql`).

Применять **только** к тестовой базе или специально созданной копии:

```powershell
.\.venv\Scripts\python.exe migrate.py status --database digital_store_test
.\.venv\Scripts\python.exe migrate.py apply  --database digital_store_test
```

Миграции никогда не запускаются автоматически при импорте модулей или старте сервера.
