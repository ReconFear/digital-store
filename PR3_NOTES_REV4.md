# PR 3 rev4 — ссылка при повторной сверке и запрет HTTP-перенаправлений

Основа — `digital-store-pr3-rev3.zip`, работа в отдельной копии. Миграции `0000`–`0002` не изменены ни на байт. Изменена `0003` (на Windows ещё не применялась), `schema.sql` пересобран. Все исправления rev2 и rev3 сохранены:
- аренда событий с `lease_token`;
- блокировка новых попыток при неразрешённой;
- проверка ответа на создание;
- раздельные роли PostgreSQL;
- `refunds_guard` и возвраты в валюте полученных денег.

Основная база `digital_store` не использовалась.

## 1. Ссылка, появившаяся при повторной сверке — исправлено (блокирующий баг)

**Воспроизведено на коде rev3** новым сквозным тестом: после повторного `GET` попытка становилась `pending` с `confirmation_url = NULL`. Сценарий:
1. ответ на создание потерян;
2. через сутки поиск в списке находит `pending` без ссылки;
3. затем `GET` возвращает тот же `pending`, но уже со ссылкой.

**Причина** — как в ревью: при `needs_bind = False` ссылку никто не передавал в базу, а `payment_record_provider_state` переводил попытку в `pending` без неё.

**Исправление:**

| Где | Что |
|---|---|
| `payment_record_provider_state(…, p_confirmation_url TEXT DEFAULT NULL)` | «Потерянная» попытка (`unresolved_attempt` без решения и без учтённых денег) переводится в `pending` **только вместе со ссылкой** — одним `UPDATE` под уже взятой блокировкой строки платежа (`FOR UPDATE`) и заказа, после проверки, что ID платежа совпадает с привязанным. Ссылки нет или она не `https://хост/…` — попытка остаётся `requires_action`, ответ `no_valid_confirmation_url`. В журнал — `payment.unresolved_resumed` |
| `payments_guard` | Переход `requires_action → pending` без https-ссылки запрещён для всех, включая владельца таблиц |
| `payments/service.py` | Ссылка передаётся в функцию только после полной проверки ответа провайдера: metadata, магазин, режим `test`, сумма, валюта, согласованность `status`/`paid`, https и домен из `YOOKASSA_CONFIRMATION_HOSTS`. Так и при первой находке, и при повторной сверке уже привязанного платежа |

Новые попытки по-прежнему блокируются, новый платёж не создаётся, покупатель продолжает **тот же** платёж по **той же** ссылке. Для обычных (не «потерянных») попыток параметр игнорируется: сохранённая ссылка не перезаписывается.

## 2. Утечка ключа ЮKassa через HTTP-перенаправление — исправлено

**Подтверждено.** Тест `test_unpatched_urllib_would_leak_the_secret` показывает: стандартный `urllib` по ответу 307 отправляет запрос на посторонний сервер вместе с `Authorization: Basic shopId:секрет`. Адаптер rev3 действительно следовал перенаправлениям: на коде rev3 новые тесты фиксируют обращение к постороннему серверу.

**Исправление** (`payments/yookassa.py`):
- Обработчик `_NoRedirect` заменяет стандартный `HTTPRedirectHandler` (проверено: в цепочке обработчиков стандартного больше нет). Запрос по адресу из `Location` не выполняется никогда, ни на чужой, ни на тот же домен.
- Ответ 3xx — `ProviderUnavailable` («результат неизвестен»), **без повтора**, `Location` в журнал не пишется.
- Для `POST /payments` это не отказ: попытка остаётся `unknown`, а не `failed`. Новая попытка не открывается. Следующий checkout или сверка обращается к API ЮKassa (не по `Location`) с **тем же** ключом идемпотентности.
- Для `GET` — событие уходит в повтор с паузой, заказ не меняется.
