# Аккаунты покупателей (PR6) — эксплуатация

Контракт HTTP API для frontend — [FRONTEND_ACCOUNTS_API.md](FRONTEND_ACCOUNTS_API.md). Роли PostgreSQL и установка `pgcrypto` — [DB_ROLES.md](DB_ROLES.md). Проверки CI — [CI.md](CI.md).

> **Не включать аккаунты на публичном магазине.** Пока не реализованы и не проверены **подтверждение email** и **восстановление забытого пароля**, аккаунты и регистрация допустимы только в закрытом тестовом окружении по отдельному согласованию. Этот документ описывает, как устроена система и как её безопасно настроить, — это не инструкция к публичному запуску.

## 1. Состояние

- Реализованы HTTP-маршруты `/api/account/*`: регистрация, вход, выход, «выйти везде», смена пароля, профиль, список и просмотр своих заказов.
- Новый заказ `POST /api/v2/orders` привязывается к аккаунту, если запрос пришёл с действительной cookie сессии и CSRF-токеном (в одной транзакции с заказом).
- Гостевые покупки по секрету заказа `access_token` работают как прежде и от аккаунтов не зависят. API v1 не менялся.
- **По умолчанию всё выключено:** `DS_ACCOUNTS_ENABLED` не задан (off), в базе `auth_settings.accounts_enabled = false` и `registration_open = false`. Пока аккаунты выключены, маршрутов `/api/account/*` нет (404), cookie сессии не читается, файл секретов не открывается, CORS — прежний (без credentials).

## 2. Как устроено включение

Аккаунты работают, только если включены **одновременно** в двух местах:

| Где | Настройка | Значения |
|---|---|---|
| Процесс приложения | `DS_ACCOUNTS_ENABLED` | `on`, `true`, `1`, `yes` — включено; `off`, `false`, `0`, `no` или пусто — выключено; любое другое значение — **ошибка запуска** (опечатка не включает аккаунты) |
| База | `auth_settings.accounts_enabled` | `false` по умолчанию |
| База | `auth_settings.registration_open` | `false` по умолчанию; при `false` регистрация — `403 registration_closed`, вход для существующих аккаунтов работает |

Штатный способ изменить флаги базы — функция `admin_auth_settings_update(accounts_enabled, registration_open)` под персональной ролью из группы администраторов (проверка `shop_require_admin`, запись в журнал аудита). Роль приложения `app` таблиц аккаунтов не видит и флаги менять не может.

Если в базе аккаунты выключены, а в процессе включены: регистрация и вход — `404`, существующие сессии на время выключения недействительны (`401`), после повторного включения снова действуют.

### Что обязательно при `DS_ACCOUNTS_ENABLED=on`

Без любого из пунктов приложение **не запустится** (лучше не запуститься, чем открыть доступ):

1. `DS_ACCOUNT_SECRETS_FILE` — путь к файлу секретов (раздел 3).
2. `ACCOUNT_TRUSTED_ORIGINS` — точные HTTPS-адреса страниц магазина через запятую (`https://хост[:порт]`, без `*`, `null`, пути и завершающего `/`; IDN — в punycode). Собственный адрес магазина входит **явно**, даже если frontend и API на одном адресе: браузер присылает `Origin` и на запросы своего сайта. По этому списку проверяются `Origin` всех изменяющих запросов аккаунта и заказа с cookie.
3. `CORS_ALLOWED_ORIGINS` — задан **явно**: пустое значение — frontend и API на одном адресе; иначе точные адреса, каждый из которых есть в `ACCOUNT_TRUSTED_ORIGINS`. В режиме аккаунтов CORS разрешает cookie (`allow_credentials`) и заголовок `X-CSRF-Token`, поэтому адреса разработки по умолчанию (`http://localhost…`), шаблоны и `*` запрещены.

### HTTPS, cookie, CSRF

- Cookie сессии: `__Host-ds_session`, `Secure; HttpOnly; SameSite=Strict; Path=/`, без `Domain`, `Max-Age` 90 дней. Браузер принимает её **только по HTTPS** — магазин с аккаунтами работает только через HTTPS; послаблений для `http` нет.
- `SameSite=Strict`: frontend и API должны быть на одном сайте (один регистрируемый домен).
- CSRF-токен = HMAC от хэша токена сессии на ключе `ACCOUNT_CSRF_KEY`; frontend получает его из `GET /api/account/me` и передаёт в `X-CSRF-Token`. Требуется для «выйти везде», смены пароля и заказа с cookie.
- В базе хранятся только SHA-256 токенов сессий; сам токен знает только браузер.

### Обратный прокси

- TLS завершается на прокси; заголовок `Origin` прокси должен передавать без изменений.
- `TRUSTED_PROXY_IPS` — адреса прокси. Только от них приложение принимает `X-Forwarded-For`. Если список пуст, а приложение за прокси, все клиенты видны с адреса прокси и лимиты по IP срабатывают для всех сразу — об этом предупреждение в журнале при запуске.
- Лимиты частоты приложения (регистрация 1/мин, вход 10/мин, смена пароля 5/мин на IP; вход и регистрация 60/мин на процесс; общие лимиты заказов) хранятся **в памяти каждого процесса**: при N процессах фактически до N× этих значений, после перезапуска счётчики сбрасываются. Общий предел обязателен на прокси (`limit_req`). При заданном `WEB_CONCURRENCY` > 1 предупреждение в журнале называет фактический множитель.
- Дополнительно база ограничивает попытки входа: `login_limit` (10) за `login_window` (15 минут) — это общий счётчик, не зависящий от процессов.

## 3. Секреты

### Формат файла

Отдельный файл (путь — `DS_ACCOUNT_SECRETS_FILE`) в формате строк `ИМЯ=значение`, как `.env` (разбирается python-dotenv; кавычки допустимы). Допустимы **только** три имени:

| Имя | Формат | Обязательно |
|---|---|---|
| `ACCOUNT_PEPPER_CURRENT` | `<версия>:<base64url от 32 случайных байт>`, версия — целое 1…32767 | да |
| `ACCOUNT_PEPPER_PREVIOUS` | тот же формат, версия **меньше** текущей | только на время смены перца |
| `ACCOUNT_CSRF_KEY` | `<base64url от 32 случайных байт>` | да |

Шаблон (значения — заглушки, не использовать):

```dotenv
ACCOUNT_PEPPER_CURRENT="1:<43 символа base64url>"
ACCOUNT_CSRF_KEY="<43 символа base64url>"
```

Правила, которые проверяет приложение при запуске: все секреты различны; неизвестное имя в файле — ошибка (опечатка не должна молча оставить перец без предыдущей версии); эти имена в окружении процесса — **ошибка** (секреты не должны попадать в общий `.env`, который читают и другие процессы). Сообщения об ошибках и `repr` значений секретов не содержат.

Случайное значение формата base64url от 32 байт можно получить так (результат сразу записать в файл, не оставлять в истории команд и логах):

```bash
python -c "import base64, secrets; print(base64.urlsafe_b64encode(secrets.token_bytes(32)).rstrip(b'=').decode())"
```

### Хранение и доступ

- Файл — **вне репозитория** и вне каталогов, которые раздаёт веб-сервер; отдельно от `.env` с учётными данными базы.
- Доступ на чтение — только у учётной записи, под которой работает приложение; запись — только у администратора. **Приложение права доступа к файлу не проверяет** — их нужно выставить и контролировать при развёртывании.
- Значения секретов никогда не попадают в README, другие документы, журналы, тикеты и коммиты.

### Смена перца и ключа CSRF

Автоматической ротации нет; новые значения читаются только при запуске — после правки файла перезапускаются **все** процессы приложения.

- **Перец.** Поддерживается период перехода: старый перец переносится в `ACCOUNT_PEPPER_PREVIOUS` (со своей версией), новый — в `ACCOUNT_PEPPER_CURRENT` с большей версией. Покупатель, вошедший в этот период, получает хэш под новой версией. Покупатель, не входивший до удаления `ACCOUNT_PEPPER_PREVIOUS`, войти больше не сможет (`invalid_credentials`; в аудите `auth.pepper_missing`), а восстановления пароля нет. Инструмента, показывающего, когда переход завершён, нет — поэтому при текущей функциональности предыдущую версию удалять нельзя без отдельного решения.
- **Ключ CSRF.** Поддерживается только один ключ. После замены все выданные CSRF-токены недействительны: изменяющие запросы получат `403 csrf_failed`, пока страница заново не запросит `/api/account/me`. Сессии при этом не затрагиваются.

## 4. Эксплуатация

### Сессии

| Параметр (`auth_settings`) | По умолчанию | Смысл |
|---|---|---|
| `session_idle` | 30 дней | срок без активности |
| `session_absolute` | 90 дней | максимальный срок сессии |
| `session_touch_interval` | 10 минут | как часто `/api/account/me` продлевает срок простоя |

Сроки проверяются базой при каждом запросе по текущему времени сервера; `Max-Age` cookie — лишь верхняя граница хранения в браузере.

Отзыв сессий:

- `POST /api/account/logout` — текущая сессия; cookie удаляется всегда;
- `POST /api/account/logout-all` — все сессии покупателя;
- смена пароля — все остальные сессии, выдаётся новая;
- вход с cookie прежней сессии того же покупателя — прежняя отзывается;
- администратор (персональная роль группы `admin`): `admin_customer_revoke_sessions`, `admin_customer_disable` (вход как при неверном пароле, сессии отозваны), `admin_customer_release_email` (освобождение адреса).

### Очистка устаревших данных

Функция `auth_maintenance_purge()` удаляет записи ограничения попыток старше `login_window` и сессии, истёкшие или отозванные более суток назад (до 10 000 строк каждого вида за вызов). Право на неё выдано роли `worker`.

Её вызывает отдельный процесс (не платёжный обработчик и не worker выдачи — сбой очистки не должен их останавливать):

```bash
python -m accounts.maintenance --once            # один проход; рекомендуется внешний планировщик раз в сутки
python -m accounts.maintenance --interval 86400  # или постоянно, проход раз в N секунд (60…86400)
```

- **Под ролью worker** (`<prefix>_worker`, DB_ROLES.md) — не под владельцем таблиц, мигратором или суперпользователем. Секреты аккаунтов процессу не нужны: если `ACCOUNT_PEPPER_*`, `ACCOUNT_CSRF_KEY` или `DS_ACCOUNT_SECRETS_FILE` заданы в его окружении, он не запустится.
- Пакет — отдельное соединение и одна короткая транзакция с локальными `statement_timeout = 1500 мс` и `lock_timeout = 500 мс`; пакеты повторяются, пока удалено по 10 000 строк, не больше 5 за проход (остаток — в следующем проходе). Параллельные запуски безопасны.
- Ошибка: `--once` — запись в журнал и код выхода 1; `--interval` — запись в журнал и повтор через полный интервал. Неизвестный исход COMMIT компенсации не требует. В журнале — только длительность, число пакетов и удалённых строк, тип ошибки и SQLSTATE.
- Отключение — снять задание из планировщика или остановить процесс; на платежи и выдачу ключей это не влияет.

> **Расписание не настроено:** код очистки есть, но автоматически он не запускается — задание в планировщике сервера создаётся отдельно, при развёртывании. Пока его нет, таблицы `customer_sessions` и `auth_throttle` только растут. Функция `auth_maintenance_purge` и процесс `python -m accounts.maintenance` проверены на PostgreSQL в разрешённой лаборатории (`tests/test_account_maintenance_db.py`: 13 passed, 0 skipped, во временных схемах). Развёртывание, задание в планировщике и эксплуатационная проверка на рабочем сервере — отдельные задачи.

### Ошибки и журналы

- Ответы — JSON `{"detail": {"code", "message"}}` без введённых значений, SQL и внутренних причин; непредвиденная ошибка — `500 internal_error`. Все ответы аккаунтов и заказов с cookie — `Cache-Control: no-store`.
- Журнал приложения (логгер `digital_store.accounts`) пишет только коды результатов, причины отказа проверок, тип исключения и SQLSTATE. Пароли, токены, CSRF-токены и email в журнал не попадают; в SQL уходят только SHA-256 токенов и производное от пароля значение (не пароль).
- **Журналы самого PostgreSQL не проверены:** при ошибке сервер может записать параметры запроса (хэши, производные паролей) — зависит от `log_min_error_statement` и `log_parameter_max_length`. По дизайну (REV5 §9, T-L1/Г8) эта проверка требуется **до merge** PR6; перенос возможен только отдельным явным решением владельцев (такого решения нет).

### Неизвестный исход COMMIT

- Регистрация, вход, смена пароля: если подтверждение COMMIT потеряно, приложение один раз проверяет новую сессию отдельным запросом. Cookie ставится только при подтверждённой сессии; иначе `503 service_unavailable` с `Retry-After`. Повторная регистрация в этом случае может ответить `409 email_taken` — пользователю нужно войти.
- «Выйти везде» и выход: при неизвестном исходе — `503`; повтор безопасен.
- Создание заказа: клиент получит `500`, хотя заказ мог быть зафиксирован (в том числе привязанным к аккаунту) — его `access_token` клиенту неизвестен, заказ останется неоплаченным. Повтор создаёт новый заказ (ключа идемпотентности нет). Для гостевых заказов так было и до PR6.

### bcrypt

Стоимость bcrypt — `auth_settings.bcrypt_cost` (12 по умолчанию; 4 — только для изолированных тестов). Менять её можно только до первого покупателя: база откажет позже. Число одновременных вычислений bcrypt в процессе ограничено; при перегрузке — `503 busy`. Замер не проводился; по дизайну (REV5 §9, Г7) он требуется **до merge** PR6, а затем повторяется на целевом сервере перед запуском.

## 5. Проверки и тесты

- Тесты с базой — **только** в отдельно согласованной одноразовой базе `*_test`, имя которой задано явно (`TEST_DB_NAME`); всё создаётся во временных схемах `ds_mig_*` и удаляется после теста. **Никогда** не запускать тесты на рабочей базе `digital_store` и на существующих базах (`digital_store_test`, `digital_store_roles_test`, `digital_store_pr6_proto_test` и других).
- Всегда с `PYTHON_DOTENV_DISABLED=1` и явными параметрами подключения; пароль — скрытым вводом, не из `.env`.
- Локальная роль тестов — без суперпользователя и без `CREATEROLE`. Тесты прав ролей (`DS_TEST_CREATE_ROLES=1`) создают роли кластера, поэтому выполняются только в изолированном CI в одноразовом контейнере ([CI.md](CI.md)); локально они пропускаются — это не успешная проверка.
- Офлайн-тесты аккаунтов база не нужна.

## 6. Ограничения перед коммерческим запуском

> Пункты 6–8 по дизайну (REV5 §9: T-L1/Г8, Г7, Г6/T-H8) — требования **до merge** PR6, а не только до запуска; здесь они повторены, потому что на рабочем окружении их нужно проверить ещё раз. Решения владельцев о переносе этих требований за merge нет.

1. Подтверждение email — не реализовано.
2. Восстановление забытого пароля — не реализовано (сейчас только администратор может отключить аккаунт или освободить адрес).
3. Ответы гостевого заказа с `access_token` (а также `checkout`/`status`) идут без `Cache-Control: no-store` — отдельная задача.
4. Проверка настроек прокси: `TRUSTED_PROXY_IPS`, передача `Origin`, `limit_req`.
5. Права доступа к файлу секретов — выставить и проверить при развёртывании.
6. Журналы PostgreSQL — проверить на утечку параметров запросов.
7. Замер bcrypt и ограничения одновременных вычислений на целевом сервере.
8. Браузерная проверка cookie (`__Host-`, `SameSite=Strict`) и CSRF на реальном HTTPS-стенде.
9. Денежные сценарии — на тестовом магазине платёжного провайдера (сейчас только локальный имитатор).
10. Периодическая очистка — проверена на PostgreSQL в лаборатории (13 passed, 0 skipped); при развёртывании настроить запуск `python -m accounts.maintenance` в планировщике сервера под ролью worker и проверить его на рабочем окружении.
